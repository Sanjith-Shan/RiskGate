# Stream pipeline bug log

Bugs found in `internal/stream` and in what it touched, each with what found it and what now pins it.

## Found by review before the first run against a real broker

A review of the exactly-once and ordering logic, read against franz-go v1.22.1's source, found these before any experiment ran. None showed up in the kfake tests, which is the point of writing them down: the tests at the time could not have caught them.

1. **A failed batch was checkpointed on the way out.** `Runner.batch` processes partitions in parallel, so when one task returned an error the others had already advanced their state and offsets, and some tasks' output had not been produced. `Run` then closed the client, closing left the group, leaving ran the revoke callback, and the revoke callback checkpointed: a snapshot of state whose output was never sent, followed by a commit. Those entity parts would never reach the joiner and their payments would never be decided. Fix: any batch error marks the runner crashed, so no callback checkpoints, and the restart resumes from the last good snapshot. `TestStreamCrashRecovery` covers the crash path; the error path shares it.
2. **The merger's release order was total only for unique (DT, TransactionID).** Ties were broken by heap shape, which differs after a restore. A restored aggregator could then number its outputs in a different order from the original, and the joiner, which drops anything at or below its high-water mark per aggregator, would drop a real part as a resend. IEEE-CIS ids are unique, so no run here could hit it, but a payment id that is not `txn_<n>` parses to ID 0 and would. Fix: the release key ends with (payments partition, offset), so the order is total for any input.
3. **A gap in a stateful partition's input was not noticed.** If retention trimmed the start of an entity-events or parts partition, or the topic was recreated under old snapshots, a task would rebuild state over the gap, and an unreadable snapshot fell back to an empty state silently. Fix: the internal topics keep everything (`retention.ms=-1`), a stateful task requires contiguous input offsets, and an unreadable snapshot stops the process instead of starting over.
4. **Shutdown checkpointed outside the poll gate.** Group callbacks could run during the final checkpoint and modify the task map underneath it. Fix: one mutex over the task map for the poll loop, the callbacks and shutdown. The first version of the fix held that mutex while leaving the group, and leaving runs the revoke callback, which takes the same mutex: every stage then took 30 s to stop. The stream tests caught that immediately; shutdown releases the mutex before leaving.
5. **A lost produce batch followed by acknowledged ones would leave a permanent gap.** franz-go can reset its producer id after a non-retryable error and keep sending, so a later record could be acknowledged after an earlier one was lost, and the downstream high-water mark would then treat the resend of the lost one as a duplicate. Fix: `StopProducerOnDataLossDetected`, so the process stops and restarts from its snapshot.

## Found by running on Windows

6. **Directory fsync fails on Windows, in the service and the stream store.** Both write snapshots with a temporary file, fsync, rename, and an fsync of the directory so the rename is durable. Windows cannot open a directory handle for that and returns "Access is denied", so `riskgate serve` refused to start (it records rule set version 1 the same way) the first time it ran natively on Windows for the HTTP reference run. Fix: skip the directory fsync on Windows, where NTFS journals the rename. It never showed on macOS or Linux.
7. **Kafka on Windows fails its log directory when a topic is deleted.** Not a RiskGate bug, but it shaped the experiments: the first run of the stream tests against the local broker deleted its topics on cleanup, and the broker shut down ("all log dirs have failed") on the second test. This is the long-known Windows file-rename problem in Kafka's log handling. Every run now has its own topic prefix and nothing is deleted, and `scripts/kafka_local.sh` turns off deletion and the log cleaner on Windows.

## Found by the negative control

8. **Experiment 2's checker lost its report exactly when there were mismatches.** `cmd/serveparity compare` records the largest absolute difference between the logged and the offline value of each feature. When one side is missing and the other present, that difference is infinite, and JSON has no infinity, so encoding the report failed. The error was discarded and the report file was left empty. Every real run had 0 mismatches, so it never showed. The arrival-order control in k1 is designed to produce mismatches, and among them are keys the stream had already seen when the offline replay had not yet, so a seconds-since-first value is present on one side and missing on the other. That run ended with an empty report. Fix: values missing on one side are counted separately (`values_missing_against_present`) and kept out of the maximum, and an encoding error is now an error. `TestReportEncodesWithMissingAgainstPresent` pins it. This is why a parity check needs a negative control: the check's failure path had never run.
